# Деплой на звичайний сервер або хостинг

Цей проєкт підготовлений для деплою на VPS або сервер з `Node.js 20+` і `nginx`.

## Що передати системному адміну

Передайте весь репозиторій цілком, включно з:

- `package.json`
- `package-lock.json`
- `src/`
- `public/`
- `deploy/`
- `vite.config.ts`
- `tsconfig.json`

Найпростіше: дати адміну архів усієї папки проєкту.

## Що має бути на сервері

- `Node.js 20+`
- `npm 10+`
- `nginx`

## Команди на сервері

```bash
cd /var/www/wings-bucha
npm ci
npm run build
npm run start
```

За замовчуванням застосунок стартує на порту `3000`.

## Env-змінні

Перед `npm run build` на сервері треба задати:

```bash
DATABASE_URL="postgresql://USER:PASSWORD@HOST:5432/wingsbucha_db?schema=public"
ADMIN_PASSWORD="надійний-пароль-для-адмінки"
ADMIN_SESSION_SECRET="довгий-випадковий-секрет-для-cookie"
UPLOAD_DIR="public/uploads"
PUBLIC_UPLOAD_BASE_URL="/uploads"
```

Якщо `DATABASE_URL` заданий, під час `npm run build` автоматично виконаються Prisma-міграції.

## Початкові дані (сід)

База є єдиним джерелом правди: будинки, типи, контакти, документи, хід будівництва й налаштування секцій читаються лише з неї. Усе, що видалено в адмінці, назад не повертається.

Стартовий набір (те, що раніше було вшите в код як `DEFAULT_*`) заливається **один раз**: після міграцій `npm run build` викликає `node scripts/seed.mjs`. Сід пропускається, якщо в БД уже є рядок `site_settings` з `id = 1`. Вручну:

```bash
npm run db:seed                 # залити, якщо БД ще не засіяна
node scripts/seed.mjs --dry-run # показати, що буде залито, нічого не пишучи
node scripts/seed.mjs --force   # додати відсутні стартові рядки (поверне видалені!)
```

Свіжа БД без сіду покаже порожній сайт.

## Як сайт отримує дані

Весь публічний контент (будинки, типи, контакти, налаштування й тексти секцій, документи, хід будівництва) читається **одним запитом на сервері** під час відкриття сторінки й потрапляє в першу HTML-відповідь. Браузер кешує його на 5 хвилин, тому Header, Footer, перелік будинків і сторінка порівняння не роблять власних запитів. Зміни з адмінки видно в новому відкритті сторінки одразу, а на вже відкритій вкладці під час навігації до 5 хвилин.

Сервер тримає цей контент у пам'яті 30 секунд (одна пара запитів до БД на всі відвідування) і скидає його при кожному збереженні з адмінки. Якщо БД на мить недоступна, сайт віддає останню завантажену копію замість помилки. Після перезапуску процесу кеш порожній, і перший запит потребує БД.

Тексти Hero та Footer редагуються в адмінці: «Секції сайту» → «Головний екран (Hero)» і «Підвал (Footer)». Порожнє поле на сайті не показується.

## Завантажені файли

Фото, PDF і відео з адмінки зберігаються в таблиці `uploads` (PostgreSQL) і віддаються за адресою `/uploads/<файл>`. Диск сервера для цього не потрібен. Без `DATABASE_URL` (локальне демо) файли пишуться в `UPLOAD_DIR`.

## Запуск як сервіс

У файлі `deploy/wings-bucha.service` є готовий `systemd` unit.

Що треба зробити адміну:

1. Скопіювати файл у `/etc/systemd/system/wings-bucha.service`
2. За потреби змінити `WorkingDirectory`, `User`, `Group`
3. Активувати сервіс:

```bash
sudo systemctl daemon-reload
sudo systemctl enable wings-bucha
sudo systemctl restart wings-bucha
sudo systemctl status wings-bucha
```

## Nginx

У файлі `deploy/nginx.conf` є базовий reverse-proxy конфіг.

Що треба змінити:

- `server_name` на реальний домен
- за потреби SSL через Let's Encrypt / Certbot

Після цього `nginx` має проксувати трафік на `127.0.0.1:3000`.

## Важливо

- Перед запуском у продакшні треба обов'язково виконати `npm run build`
- Серверний запуск іде через `deploy/node-server.mjs`
- Цей раннер сам віддає `dist/client` як статику і SSR-сторінки через `dist/server/server.js`
- Для продакшену обов'язково потрібні `DATABASE_URL`, `ADMIN_PASSWORD` і `ADMIN_SESSION_SECRET`
